== 1. The frame edge and the first $80C530 entry ==

  $00C0E2 is the NMI handler; run_interrupt interprets it on both
  tiers, so its entry is the frame-start sample.  It equals the
  frame-edge [frame] value exactly.

  frame   d_frame_start   d_c530_entry   in-frame drift
   1832             +14            -52             -66
   1833              +0            -40             -40
   1834             -32            +56             +88
   1835              +0             +0              +0
   1836              +0             +0              +0

  The frame edge is in phase on f1833, f1835 and f1836 and tens of
  clocks off on the others.  The in-frame drift is not monotone and
  is zero on two of the five frames: it is a per-frame offset, not a
  tax that accumulates with work done.

== 2. The frame runs in lockstep almost everywhere ==

  Entry sequences are compared position by position (both legs run
  the same guest code up to the first body only the seed compiles).

  f1835: 51 shared entries before the sequences diverge; 46 have d=0; distinct d [-40, 0]
  f1836: 51 shared entries before the sequences diverge; 45 have d=0; distinct d [-40, 0]

  A non-zero d here is a single instruction's charge landing on one
  side of a call boundary: it cancels at the next entry.  Example
  from f1835, entries 2-4 (pc, master):
    2: ctrl 818877 656099164   seed 818877 656099164   d=+0
    3: ctrl 818076 656099364   seed 818076 656099324   d=-40
    4: ctrl 809D9D 656099522   seed 809D9D 656099522   d=+0
    ctrl spends 200 then 158 clocks; seed spends 160 then 198.  The
    interval totals match; only the split at the entry differs.

== 3. The one body that differs on this path ==

  $80ABBC is the top of the loop inside $80AD9F, the second body
  round 6 found necessary.  Seed compiles it; control interprets it.
  Both enter it 18 times in these frames.

  frame   n   ctrl loop   seed loop   seed-ctrl
   1832  18       10174       10174          +0
   1833  18       10214       10174         -40
   1834  18       17850       17898         +48
   1835  18       10174       10174          +0
   1836  18       10174       10174          +0

  On f1832, f1835 and f1836 the loop costs the same 10,174 master
  clocks on both tiers.  On f1833 it costs the control 40 more, and
  on f1834 the seed 48 more.  Subtract the loop delta from the
  in-frame drift to $80C530:

  frame   loop delta   in-frame drift   residual
   1832           +0              -66        -66
   1833          -40              -40         +0
   1834          +48              +88        +40
   1835           +0               +0         +0
   1836           +0               +0         +0

  The residual is zero on f1833, f1835 and f1836: there the whole
  in-frame offset is the $80AD9F loop's own boundary charges.  On
  f1834 it is +40, a second boundary.  On f1832 it is -66 and the
  loop is in phase, so the offset was created in the frame's
  opening, in the first two entries after the NMI return:
    0: ctrl 80C11F 655005716   seed 80C11F 655005730   d=+14
    1: ctrl 81A99D 655006090   seed 81A99D 655006144   d=+54
    2: ctrl 80C399 655016180   seed 80C399 655016128   d=-52

== 4. What this changes ==

  The seam is not drifting.  At the frame edge the clocks agree on
  most frames, and inside a frame almost every shared function entry
  has d=0 to the clock.  The phase at the read is a small per-frame
  offset (0 to +-56), created at one or two call boundaries and
  sometimes zero for a whole frame.

  That is why a read-time fix cannot be sufficient.  On f1835 and
  f1836 the tiers enter $80C530 at the same clock, so the only
  difference at the latch is the 24-clock in-body convention; on
  f1832/f1833/f1834 they enter tens of clocks apart for reasons that
  are already decided before the body runs.  Round 7 measured the
  read; this round shows the entry term is a small discrete offset,
  not the accumulating drift the seam report warned about.

  It also leaves the gate's first byte unexplained by the latch:
  the first $80C530 entry on both tiers is f1832, while the first
  non-label state byte is $7E00126 at f1830.

== 5. The counter that does drift ==

  The same [frame] lines carry cpu->cycles ('trunk').  It is the
  counter the upstream seam report found drifting; master_cycles is
  not.  At the frame edges in this window:

  frame   d_master   d_trunk
   1828        +14       -144
   1829        -20       -149
   1830        +14       -144
   1831        +14       -144
   1832         +0       -713
   1833        -32      -1623
   1834         +0      -1624
   1835         +0      -1623
   1836         -6      -1624

  d_master stays inside a few tens of clocks; d_trunk grows by
  hundreds and then thousands.  A gate built on master_cycles sees a
  nearly path-invariant clock; a budget built on cpu->cycles sees the
  seam.  Round 7's read is priced in master clocks, so it moved a
  clock that was already within tens of clocks of the control.  The
  counter carrying the accumulated drift is cpu->cycles, and it is
  not what the PPU latch samples.

== 6. The gate, instrumentation inert ==

  first state byte differing: f1830
  frames differing: 305 of 4575, 895 bytes
  crc32_wram first diff: f1828 0xB615CF19 vs 0xC912779D

  Same binaries as the probe runs, all three env vars unset: it
  reproduces the round-7 gate exactly (f1830, 305 of 4575, 895
  bytes, crc f1828), so the taps do not perturb the run.

  +  if (!r8_anchor_init) {

  +    r8_anchor_init = 1;

  +      const char *q = e;
  +      while (*q && r8_anchor_n < 8) {
  +        char *end = NULL;
  +        unsigned long v = strtoul(q, &end, 16);
  +        if (end == q) break;
  +        r8_anchor_pcs[r8_anchor_n++] = (uint32_t)v;
  +        q = end;
  +        if (*q == ',') q++; else break;
  +      }
  +    }
  +  }
  +  for (int i = 0; i < r8_anchor_n; i++)
  +    if (pc24 == r8_anchor_pcs[i]) return 1;
  +  return 0;
