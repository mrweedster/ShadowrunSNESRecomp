# M1/M2 promotion, round 5: authorising the state/event dispatch

Date: 2026-11-08. Branch: `main`. Everything below is a measurement.

Round 4 left `$80F4F9` unauthorised, so any compiled body that reached that
stub abandoned instead of transferring (`m2_promotion_round4.md` §6). This round
adds the authorisation, re-baselines the pair that ships, and re-tests the six
seeds that round 4 could not run past the stub. It ships one config decision and
no new seed.

**What shipped**: the hand-written

```
indirect_dispatch f4f9 50 ptrtail targets:...
```

block at the end of `recomp/bank80.cfg` (`artifacts/round5_directive.txt`). Its
target count and the instruction at the site are re-derived there: 50 targets,
no duplicates, `$80F4F9` is `6C A2 00`, `JMP ($00A2)`.

The shipped pair's *identity* moves because the manifest now records the
dispatch vocabulary: executable `2b478e8d26bb27f9 -> a0587ed0a0e34687`, program
digest `eea52f0716ab0f40 -> aa4a6f28a00afdb2`, manifest `eea52f07 -> aa4a6f28`
(`artifacts/round5_variant_ledgers.txt`,
`artifacts/round5_directive_inert.txt`). The generated machine code does **not**
move: every instruction-bearing file is byte-identical, and the only changes in
the whole generated set are `module_v2.c`'s two digest strings and the manifest's
`exit_modes` (+70 entries). On the combat route the pair's counters are
identical to round 4's to the unit: interp `90.04 %` / AOT `9.96 %`,
`interp_cycles 860,839,515`, `cpu_cycles 956,096,571`,
`master_cycles 7,878,127,092` (`artifacts/round5_variant_ledgers.txt`,
`artifacts/round4_variant_ledgers.txt`).

**What did not ship**: the six seeds round 4 blocked. With the directive, five
now reach the route end (`exit=0`, `script quit after 22044 frames`) and
`$80F495` stops at a different gate (`exit=3`, `until 001F0 timed out after 900
frames` at 21639). All six still fail the state gate with the same onset,
`frame_001828`, `2745 of 4575 frames differ`
(`artifacts/round5_sweep.tsv`). The gate, not the cycle share, is the decision.

## 1. The question, and the rules it is answered under

Round 4 ended with a measured reason to stop seeding: 69.25 % of the
interpreted residue is interpreted at PCs with no manifest node
(`artifacts/round4_hot_vs_aot.md`, the `no-node` row). It also ended
with six seeds that could not be judged, because a seed that reaches `$80F4F9`
without an authorisation abandons there. The question this round answers is
narrow: **does authorising the dispatch let those seeds be judged, and does
anything about the shipped pair move when it does?**

The rules are the round-4 rules, unchanged:

* a seed is adopted only if its compiled bodies compute the same machine state
  as the control; cycle-share movement alone is not a win;
* a claimed difference has to clear the same-binary replicate spread; wall
  clock is a result, not a note;
* no harness leg may reach the ROM file-picker: every launcher passes `--rom`
  or sources `tests/rom.sh`;
* seed tables are generated by `tests/gap_seeds.py`, never hand-edited;
* identity-sensitive legs run from a scratch anchor, never inside `build-*/`;
* every number in this record appears in an artifact under
  `evidence/artifacts/`, and `tests/round5_artifacts.sh` regenerates those
  artifacts from files that already exist.

## 3. What the directive says, and what the stub is

`artifacts/round5_directive.txt` extracts the hand-written block verbatim and
parses it, rather than restating it. The line is

```
indirect_dispatch f4f9 50 ptrtail targets:808371,...,80E22C
```

and the parser reports `parsed targets 50  duplicates 0  count matches
declaration: True`. The site is `$80F4F9 -> ROM $0074F9: 6C A2 00`, decoded as
`JMP ($00A2)`: an indirect tail transfer whose pointer is written by the game's
state machine, not by this routine.

That is why the analyzer cannot recover the target set from the routine, and why
the target list is the round-3 combat capture's own discovery rows at this site
(50 handlers over 222,623 hits; the block's own comment records the count). The
mode is `ptrtail`: a listed pointer transfers to the handler and the handler's
`RTS` is inherited from the caller. Any unlisted pointer takes the emitted
`default:`, `interp_tier_dispatch_tail`, so authorising this site cannot drop a
transfer.

targets plus 20 discovered descendants of the pointer-mode analysis; they are

One consequence is worth stating because it invalidates a round-4 convenience:

`round4_manifest_r4base.json.bz2` (`240af24b`), 269 nodes and 229 exit modes.
So the directive is inert on the control as well: the site node is not in that
program, and no target is registered.

## 8. What the gate divergence is

The sweep's gate is the run's own per-frame WRAM checksum: `tests/parity.sh`
compares the `crc32_wram` each frame dump carries, so the verdict names a frame
and includes the label bytes (the frame-kernel counter window and the timer
singletons that `framedump_diff.py` would excuse). `artifacts/round5_sweep.tsv`
therefore says, for all six seeds, only `first divergence at frame_001828;2745
of 4575 frames differ` — a frame, not a byte.

The byte-level reading of this onset on this route comes from round 4's
rejected `$80ABBC` on the same probe route (`artifacts/round4_state_bytes.md`,
`shift probe: s80ABBC`). There the checksum divergence is also
`frame_001828;2745 of 4575`, and `framedump_diff.py state` resolves it: the
`f1828` checksum difference is a label byte, the first non-label byte is
`$7E00126: 88 -> 85` at `f1830`, and `f1832` carries 12 state bytes including
`$7E00000-$7E00006` and `$7E00134-$7E00136`. That is the pattern this round
tested on its own seed.

`artifacts/round5_gate_writer.txt` runs `tests/latch_writer.py` on the same
parity route and the same two trace builds (control vs the `$80C1C9` seed),
paging the `$0126/$0127` write record up to the onset. It reports:

```
['0126', '0127']: identical byte value sequences
```

`artifacts/round5_gate_state.txt` reads the same two legs at frame boundaries
with `tests/latch_state.py`, separating live stack (address `>= S`) from dead
scratch (`< S`):

```
f1830/1830: DP identical=True latch identical=True live-stack diffs=0 below-S diffs=0
f1832/1832: DP identical=True latch identical=True live-stack diffs=0 below-S diffs=0
f1834/1834: DP identical=False latch identical=True live-stack diffs=1 below-S diffs=6
   live: [('$013A', '3B', '11')]
   below-S: [('$0134', '04', '88'), ...]
f1836/1836: DP identical=False latch identical=True live-stack diffs=0 below-S diffs=0
f1838/1838: DP identical=False latch identical=True live-stack diffs=1 below-S diffs=6
```

On this seed the `$0126/$0127` split does not reproduce: both legs write the
same value sequence, and the latch bytes agree at every sampled boundary. What
does reproduce is the cluster round 4 saw — the direct page differs at every
sampled boundary from `f1834` on, the live stack byte `$013A` is `3B -> 11` at
`f1834` and `f1838`, and the dead scratch `$0134-$0137` moves with it. So the
rejection does not rest on the first label byte the checksum names, and it does
not rest on `$0126` scratch either; it rests on a persistent guest-state
divergence in the direct page and the `$0134-$013A` cluster. The probe
localises it but does not name the writing body; that is the next round's
experiment.

## 9. The combat-route latch writer

The same question was asked on the combat route, where the first `$0126` split
is much later. `artifacts/round5_latch_split.txt` (`tests/latch_writer.py`,
`--park 16200`) names the writer:

```
$0126: first byte value split at write #1412
  ctrl: #1412 f14664 =9E pc=0x809e3e func=interp@$809E00
  seed: #1412 f14664 =80 pc=0x809e39 func=(none)
        #1413 f14664 =9E pc=0x809e3e func=interp@$809E39
```

The writer is the decompressor at `$809E01` / `$809E1E` (`STA $0000,X` at
`$9E59`). The seed emits one transient `$80` at the AOT side of the seam; the
control enters at `$809E00` interpreted and writes `$9E`. The next write is
`$9E` on both legs. The `$0127` split at `f16142` (`BC` vs `B9`) also resyncs.
`artifacts/round5_latch_state.txt` samples frame boundaries around both splits:
DP, `S`, and the live stack agree; the only differing bytes are below `S`, i.e.
dead scratch.

`cpu_cycles` drifts by `-2,565` to `-2,788` while `master_cycles` drifts by
`-12` to `+18` over the same samples. That is a bookkeeping/phase difference
at the seam, not a wrong computed value; it does not by itself explain the
`f1828` gate divergence, which is a different route and a different event. The
two findings are kept separate here on purpose; the seam half is written up in
`evidence/upstream_seam_cycle_bookkeeping.md`.

## 11. Decision record

1. **Ship the directive.** It is the correct reading of `JMP ($00A2)`, it
   cannot drop a transfer (unlisted pointers take the interpreter tail), and it
   is machine-code-inert on the shipped pair. The pair's identity is
   re-baselined to executable `a0587ed0a0e34687`, manifest `aa4a6f28a00afdb2`,
   generated-set archive `c52a74911a813662`.
2. **Ship no new seed.** All six seeds the directive unblocked still fail the
   state gate at `frame_001828`; five fail it after reaching the route end, one
   (`$80F495`) fails a different gate as well.
3. **Keep `$80F4F9` authorised.** The six seeds' failure is their compiled
   bodies, not the authorisation: the shipped pair carries the same directive
   and is byte-identical to the control at 22 checkpoints and over 4,575 frame
   dumps.
4. **Do not re-use round-4 digests** for a rebuild of this tree. The program
   digest moved because the manifest's `exit_modes` moved, even though no
   instruction body did.

## 12. What the next round should do

* Sweep on top of the shipped pair, not on top of the bare control. The right
  question for a candidate seed is `pair + seed` against `pair`; this round's
  `base + seed` design answers the weaker question and cannot tell a seed that
  only interacts with the pair from one that is clean on its own.
* Treat the `f1828` divergence as a cluster property. Six distinct seeds and
  round 4's `$80ABBC` all produce the same gate onset, and round 5's probe
  reproduces the `$0134-$013A` cluster that round 4's byte diff named; a useful
  next experiment narrows the compiled cluster (one body at a time, or a
  hand-built minimal root) until the body that moves those bytes is named.
* Give `$001F0` its own gate. It is not a dispatch question, and a seed that
  reaches `until $001F0` has already done everything the dispatch can do.
* Carry the seam's cycle bookkeeping upstream. The AOT/interpreter transition
  writes the same value one store later and books `-2,565` to `-2,788`
  `cpu_cycles` differently while `master_cycles` moves by at most 32 over the
  two probes. The relevant code is the pinned framework's
  `runner/src/snes/interp_bridge.c` and `runner/src/common_cpu_infra.c:880-935`;
  the seam half is written up in `evidence/upstream_seam_cycle_bookkeeping.md`.
  Its §8 experiment is done and the report carries the result: the common AOT
  block set is identical over all 1,610 entries in f1820-1834, while the seeded
  cluster first moves at f1832 (two entries) — the frame the park probe already
  shows `−144` with DP identical, two frames before the f1834 state split — so
  the counter tracks phase there, and only the `−149` at f1830 remains, a
  sub-block charge that needs an instruction-level AOT log
  (`artifacts/round5_seam_phase.txt`).

Round 6 took the first two bullets: `m2_promotion_round6.md` rebuilds the
rejected `$80C1C9` seed as `pair + seed`, reproduces this round's gate onset
exactly, and narrows the added AOT bodies to the 1-minimal pair `$80AD9F` and
`$80C530`. It ships nothing: the two-body demotion restores the pair but keeps
3.4 % of the seed's cycle gain, and `$80C530` reads the PPU counters, so the
next lever is pricing that read on the AOT tier rather than another seed.
